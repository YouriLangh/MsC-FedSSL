For our data splits: 
Following FedMatch~\cite{FedMatch} and SemiFed~\cite{semifed}, we assume data is partitioned among clients, with each client holding a mixture of labeled and unlabeled samples. The central server only serves to aggregate client models and redistribute the aggregated model in each round. We thorougly explore two scenarios: the IID setting and the non-IID setting.

In the IID case, the dataset is first shuffled before it is split into a labeled and unlabeled dataset. This labeled dataset consists of either a fraction of the dataset in case either the "labeled\_fraction" or the "labeled\_total" parameters are given or, the dataset is sorted by its targets and we retain only a number of samples per class in the case the "labeled\_per\_class" parameter is given.  The unlabeled and labeled datasets are then shuffled again before being split into equal portions across clients. This approach is in line with prior work \todo[color=yellow]{verify this}.


In the non-IID case, SemiFed~\cite{semifed} constructs the partition by first selecting a fixed number of labeled samples (e.g., 1K, 2K, 4K) and then distributing both the labeled and unlabeled data in a non-IID manner across clients. We adopt a similar setup, similarly to the IID case, we shuffle the dataset and then allow people to choose either a number of labeled samples for an experiment (labeled\_total or labeled\_fraction) or the number of labels per class. This splits the dataset into a labeled subset and an unlabeled subset. These subsets are then both distributed in a non-IID fashion, where both label and quantity skew are simulated using a Dirichlet distribution for each client over each class. Depending on the Dirichlet \alph chosen, this can result in some clients have very few or no labeled samples. We argue that this approach is required as it allows for comparison between both the IID and non-IID case.

For the final one, the data given to the client is shuffled and yet again only a slice is labeled (this is even stricter.)
